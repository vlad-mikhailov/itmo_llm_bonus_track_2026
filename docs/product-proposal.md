# Product Proposal

## Обоснование идеи

Существующие туристические решения (TripAdvisor, Google Maps, Lonely Planet) предоставляют одинаковую информацию всем пользователям без учёта их интересов, уровня знаний и контекста путешествия. Живой гид решает эту проблему, но недоступен большинству путешественников по цене и логистике.

AI Adventure Guide занимает нишу между "безликой энциклопедией" и "живым гидом": система накапливает знания о пользователе, адаптирует глубину и стиль ответов, комбинирует несколько источников информации, умеет распознавать места по фото и помнит историю взаимодействия.

Существующий MVP (RAG-пайплайн + Telegram-бот + база Wikivoyage + распознавание фото) подтвердил техническую осуществимость. В рамках курса система доработана до полноценного агента с памятью, инструментами и измеримым качеством.

---

## Цель и метрики

**Цель:** создать агента, который даёт персонализированные, контекстно-релевантные ответы на вопросы о путешествиях, работает с фото и помнит историю взаимодействия с пользователем.

### Продуктовые метрики

| Метрика | Цель PoC |
|---|---|
| Доля ответов, оценённых пользователем как полезные | ≥ 70% |
| Доля корректно отклонённых off-topic запросов | ≥ 90% |
| Доля ответов, использующих историю пользователя | ≥ 50% |
| Точность распознавания места по фото | ≥ 70% |

### Агентские метрики

| Метрика | Цель PoC |
|---|---|
| Точность выбора инструмента (RAG / Weather / Wikipedia / Vision) | ≥ 80% |
| Качество ответов по RAGAS (faithfulness + relevance) | ≥ 0.7 |
| LLM-as-judge оценка на тестовой выборке из 30 пар | ≥ 4/5 |
| Успешный Wikipedia fallback при низком FAISS score | ≥ 85% случаев |

### Технические метрики (SLO)

| Метрика | Цель |
|---|---|
| p95 latency — текстовый запрос | ≤ 8 секунд |
| p95 latency — распознавание фото | ≤ 10 секунд |
| Uptime | ≥ 95% |
| Успешный retrieval (найден хотя бы 1 релевантный чанк) | ≥ 85% запросов |

## Сценарии использования

### Основные сценарии

**Культурный вопрос:** "Почему в японских храмах хлопают в ладоши?" → агент достаёт контекст из Wikivoyage + Wikipedia, отвечает с учётом того, что пользователь уже спрашивал про Японию.

**Фото достопримечательности:** пользователь отправляет снимок здания → агент распознаёт место через vision-модель, рассказывает историю и культурный контекст.

**Практический вопрос с погодой:** "Стоит ли идти в Колизей сейчас?" → агент проверяет погоду через OpenWeatherMap и добавляет практические советы.

**Персонализация:** пользователь, который раньше спрашивал про архитектуру, в follow-up вопросах ("что ещё посмотреть?") получает контекстный ответ с учётом истории диалога.

**Wikipedia fallback:** вопрос про малоизвестное место с низким FAISS score → агент автоматически обращается к Wikipedia и использует результаты как дополнительный контекст.

### Edge-кейсы

| Сценарий | Ожидаемое поведение |
|---|---|
| FAISS не нашёл релевантных чанков | Fallback на Wikipedia API; если и там нет — агент честно сообщает об ограниченности базы |
| Вопрос вне тематики (рецепты, финансы) | Guardrail отклоняет запрос, объясняет специализацию бота |
| Follow-up вопрос без явного контекста ("а что там ещё?") | Пропускается guardrail, память подтягивает предыдущий контекст |
| Фото без явной достопримечательности (еда, селфи) | Агент сообщает что не смог распознать место, просит другое фото |
| Редкое место без данных в базе | Агент использует Wikipedia + общие знания модели |
| Запрос содержит prompt injection | Guardrail блокирует, продолжает работу в штатном режиме |
| Пользователь запрашивает /forget | Профиль и история удаляются, хешированный id больше не хранится |

## Ограничения

### Технические

- Контекстное окно модели ограничено: хранятся последние 10 пар сообщений на пользователя (in-memory, не персистентно)
- FAISS-индекс статичен: новые данные требуют переиндексации
- OpenWeatherMap бесплатный тариф: лимит 1000 запросов/день
- Распознавание фото работает только для известных достопримечательностей
- Wikipedia API иногда возвращает нерелевантные статьи при широких запросах

### Операционные

- Стек: OpenRouter API (DeepSeek, Gemini) + OpenWeatherMap + Wikipedia API — всё на бесплатных/дешёвых тирах
- База знаний покрывает популярные направления, редкие места могут давать пустой retrieval

## Архитектурный набросок

```
Пользователь (Telegram)
   текст или фото
        ↓
[Guardrail] — prompt injection + off-topic фильтр
   off-topic → отказ
        ↓
[Query Rewriter] — LLM переформулирует вопрос, извлекает entities
        ↓
[Tool Router] — решает какие инструменты нужны
   ├── FAISS Retriever (Wikivoyage)   — основной источник
   ├── Wikipedia API                  — fallback при низком score
   ├── OpenWeatherMap API             — погода
   └── Vision Model (Multimodal LLM) — распознавание фото
        ↓
[Generator] — синтезирует ответ из контекста + истории диалога
        ↓
[Memory Manager] — сохраняет в профиль пользователя (SHA-256)
        ↓
Ответ → Пользователь

[User Profile (in-memory)]
   - хешированный user_id
   - история последних 10 диалогов
```
